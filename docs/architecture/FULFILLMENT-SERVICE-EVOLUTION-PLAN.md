# fulfillment-service 创建准入与演进计划

## 1. 第一批评审结论

选择持久化履约编排作为独立业务边界。履约拥有商家操作的受理、执行步骤和恢复决定。当前 CREATE 结论为
`REJECTED`：持久流程、接收方幂等和订单竞态保护尚待实现。现有履约继续由 commerce 执行。

代码基线已将商家身份转换留在 Controller，将物流投影写入收口到 LogisticsService。发货仍分段执行本地投影、
物流平台请求和远程订单更新。commerce 事务无法回滚已经成功的远程调用。商家确认/发货的状态更新和订单事件目前
也是独立远程操作。物流模拟器按商家运单号查找已有记录，仍须验证并发和异正文冲突，才可作为可靠重放依据。

## 2. 唯一所有权

| 边界 | 权威事实 |
| --- | --- |
| order-service | 订单、地址快照、订单事件、订单状态与发货准入条件 |
| payment-orchestration-service | 支付、退款与资金处理 |
| inventory-service | 库存与库存流水 |
| commerce 内 logistics | `shipment_records`、`shipment_events`、`shipment_notifications`，物流回调与对账 |
| 物流模拟平台 | 渠道运单与轨迹事实 |
| fulfillment | 商家命令及结果、履约执行步骤、下游命令和恢复记录 |
| commerce 商家入口 | Session、RBAC、可信 merchantId 和页面数据聚合 |

履约记录只保存稳定外部 ID、执行所需的最小请求字段、版本、渠道操作引用与步骤结果。订单和物流历史留在各自
所有者。旧订单继续可查询，且可以按当前订单与运单事实开启新操作。切换前需要识别旧路径的半完成记录，逐笔对账
并记录处置结果。历史数据无需合成为已完成的 Saga。

## 3. 持久流程与一致性

| 候选履约表 | 记录内容 |
| --- | --- |
| `fulfillment_process` | 操作归属、当前步骤、执行结果、流程版本和下游业务引用 |
| `fulfillment_command_inbox` | 商家命令 ID、请求指纹及已受理操作引用 |
| `fulfillment_command_outbox` | 下游命令、租约、重试次数和下次执行时间 |
| `fulfillment_result_inbox` | 已应用的下游结果、去重标识及关联步骤 |
| `fulfillment_recovery_record` | 人工恢复的授权人、原因、证据和操作结果 |

按商家接单、发货、修改运单三个操作分别持久化。每条操作记录当前步骤、执行状态、版本和上次错误。执行状态区分
处理中、待重试、待人工核对、成功和确定拒绝。待重试与待核对保留原步骤。每个订单同一时刻只允许一个未结束的
履约写操作。命令 Inbox、流程和第一条 Outbox 在同一事务提交。消费结果时在同一事务提交结果去重、流程推进及
下一条 Outbox。只用租约、有限退避和版本条件更新认领任务，网络调用在事务外执行。

- 接单通过 Order V1 原子地校验商家和状态、推进订单、写事件并记住命令结果。
- 发货先由 Order V1 在订单所有者内校验商家、订单状态和库存已提交，并登记持久发货意图。订单与资金路径需明确
  退款和取消与该意图的互斥规则。由订单所有者在自己的事务中执行条件竞争，避免两个调用各读到可执行后同时成功。
- 物流边界用固定运单引用创建运单。已创建后仅继续推进订单发货状态和订单事件。订单完成后记录履约成功。
- 修改运单在既有运单上执行，并通过版本防止旧命令覆盖新版。下游更新及订单事件分别保存稳定命令结果。
- 超时先按原命令 ID 或运单引用核对。只有证据证明副作用未发生，才允许按已定义的策略释放发货意图。物流已成功
  时优先正向修复。无法确认时记录待人工核对，由授权人员提供原因、证据并使用原命令 ID 恢复。

## 4. 准入门禁与批次

1. 第一批记录所有权与协议草案，收口跨模块持久化依赖，留下可复跑的只读审计。
2. 在 commerce 内按唯一写路径实现持久化流程，冻结契约，补齐 Order 原子命令、下游结果查询及库存/退款竞态门禁。
   用契约测试验证重复、冲突、乱序、掉电恢复和人工核对。在真实 MySQL 上审计异常状态和测试迁移生命周期。
3. CREATE 通过后创建分层服务及独立 MySQL，先关闭业务流量。仅对履约自有事实做可重复交接、追平、水位和隔离；
   跨进程验证幂等、超时、结果丢失、停机恢复与 Trace。
4. 独立评审 CUTOVER，在获准窗口排空旧操作、最终核对并切到唯一远程写路径，撤销旧履约表权限。完成监控与稳定性
   观察后再评估 M4 PostgreSQL 专项。

在仓库根目录运行 `scripts/windows/audit-fulfillment-admission.ps1` 或
`bash scripts/linux/audit-fulfillment-admission.sh`。脚本通过代表当前边界基线成立，末行 `REJECTED` 代表
CREATE 仍处于阻塞状态。

## 5. 第二批进展

当前商家接单、发货入口已通过 Order V1 的 `MERCHANT_CONFIRM`、`MERCHANT_SHIP` mutation 提交状态和事件。
订单库在同一事务内校验商家归属、条件更新订单、写入对应事件并保存 mutation 结果。发货更新同时检查库存为
`COMMITTED`。商家入口原有事件类型和触发来源保持兼容。

真实 MySQL 商家履约验证中，订单 `ORD-DE00215CB306474C` 的接单和发货事件各 1 条，触发来源均为 `USER`。

物流创建仍先于订单最终发货更新。后续需要在调用物流前持久化发货意图，并让退款派发在订单拒绝资格时停止渠道
投递并保存可查询的拒绝结果。持久编排、跨服务结果重放及修改运单的版本保护仍待完成。CREATE 保持 `REJECTED`。
