# fulfillment-service 创建准入与演进计划

## 1. 第一批评审结论

选择持久化履约编排作为独立业务边界。履约拥有商家操作的受理、执行步骤和恢复决定。第一批 CREATE 结论为
`REJECTED`，当时的阻塞项为持久流程、接收方幂等和订单竞态保护。现有履约继续由 commerce 执行。

第一批将商家身份转换留在 Controller，将物流投影写入收口到 LogisticsService。发货涉及本地投影、物流平台请求
和远程订单更新，commerce 事务无法回滚已经成功的远程调用。接单、发货的状态与事件已在第二批收口到 Order V1。

## 2. 唯一所有权

| 边界 | 权威事实 |
| --- | --- |
| order-service | 订单、地址快照、订单事件、订单状态与发货准入条件 |
| payment-orchestration-service | 支付、退款与资金处理 |
| inventory-service | 库存与库存流水 |
| commerce 内 logistics | `shipment_records`、`shipment_events`、`shipment_notifications`，物流回调与对账 |
| 物流模拟平台 | 渠道运单与轨迹事实 |
| fulfillment | 商家命令及结果、履约执行步骤、下游命令和恢复记录 |
| commerce 商家入口 | Session、RBAC、可信 merchantId 和页面数据聚合 |

履约记录只保存稳定外部 ID、执行所需的最小请求字段、版本、渠道操作引用与步骤结果。订单和物流历史留在各自
所有者。旧订单继续可查询，且可以按当前订单与运单事实开启新操作。切换前需要识别旧路径的半完成记录，逐笔对账
并记录处置结果。历史数据无需合成为已完成的 Saga。

## 3. 持久流程与一致性

| 候选履约表 | 记录内容 |
| --- | --- |
| `fulfillment_process` | 操作归属、当前步骤、执行结果、流程版本和下游业务引用 |
| `fulfillment_command_inbox` | 商家命令 ID、请求指纹及已受理操作引用 |
| `fulfillment_command_outbox` | 下游命令、租约、重试次数和下次执行时间 |
| `fulfillment_result_inbox` | 已应用的下游结果、去重标识及关联步骤 |
| `fulfillment_recovery_record` | 人工恢复的授权人、原因、证据和操作结果 |

按商家接单、发货、修改运单三个操作分别持久化。每条操作记录当前步骤、执行状态、版本和上次错误。执行状态区分
处理中、待重试、待人工核对、成功和确定拒绝。待重试与待核对保留原步骤。每个订单同一时刻只允许一个未结束的
履约写操作。命令 Inbox、流程和第一条 Outbox 在同一事务提交。消费结果时在同一事务提交结果去重、流程推进及
下一条 Outbox。只用租约、有限退避和版本条件更新认领任务，网络调用在事务外执行。

- 接单通过 Order V1 原子地校验商家和状态、推进订单、写事件并记住命令结果。
- 发货先由 Order V1 在订单所有者内校验商家、订单状态和库存已提交，并登记持久发货意图。订单与资金路径需明确
  退款和取消与该意图的互斥规则。由订单所有者在自己的事务中执行条件竞争，避免两个调用各读到可执行后同时成功。
- 物流边界用固定运单引用创建运单。已创建后仅继续推进订单发货状态和订单事件。订单完成后记录履约成功。
- 修改运单在既有运单上执行，并通过版本防止旧命令覆盖新版。下游更新及订单事件分别保存稳定命令结果。
- 超时先按原命令 ID 或运单引用核对。只有证据证明副作用未发生，才允许按已定义的策略释放发货意图。物流已成功
  时优先正向修复。无法确认时记录待人工核对，由授权人员提供原因、证据并使用原命令 ID 恢复。

## 4. 准入门禁与批次

1. 第一批记录所有权与协议草案，收口跨模块持久化依赖，留下可复跑的只读审计。
2. 在 commerce 内按唯一写路径实现持久化流程，冻结契约，补齐 Order 原子命令、下游结果查询及库存/退款竞态门禁。
   用契约测试验证重复、冲突、乱序、掉电恢复和人工核对。在真实 MySQL 上审计异常状态和测试迁移生命周期。
3. CREATE 通过后创建分层服务及独立 MySQL，先关闭业务流量。仅对履约自有事实做可重复交接、追平、水位和隔离；
   跨进程验证幂等、超时、结果丢失、停机恢复与 Trace。
4. 独立评审 CUTOVER，在获准窗口排空旧操作、最终核对并切到唯一远程写路径，撤销旧履约表权限。完成监控与稳定性
   观察后再评估 M4 PostgreSQL 专项。

本阶段历史准入使用运行中的 commerce-db 与 order-db。当前 `scripts/audit/audit-fulfillment-admission.ps1` 走独立执行拓扑，见第 26 节。
末行 `PASSED` 表示结构和排空条件的只读检查通过，存在未决项时脚本返回非零退出码。

## 5. 第二批进展

当前商家接单、发货入口已通过 Order V1 的 `MERCHANT_CONFIRM`、`MERCHANT_SHIP` mutation 提交状态和事件。
订单库在同一事务内校验商家归属、条件更新订单、写入对应事件并保存 mutation 结果。发货更新同时检查库存为
`COMMITTED`。商家入口原有事件类型和触发来源保持兼容。

真实 MySQL 商家履约验证中，订单 `ORD-DE00215CB306474C` 的接单和发货事件各 1 条，触发来源均为 `USER`。

订单库 V4 增加发货意图指纹。商家发货在调用物流前按订单状态、库存、商家归属和运单参数原子登记意图。
同商家同运单参数可重试，成功更新为 `SHIPPED` 时清除意图并写入订单事件。物流投影先提交，再推进订单。
已登记的意图在物流失败或响应未知时保留，商家可用相同参数重试既有物流引用。

退款派发用稳定命令 ID 调用订单退款准入。订单事务取得行锁后，在无发货意图时进入 `REFUNDING`，
同时写事件与原订单状态。拒绝时支付记录 `ORDER_REFUND_ADMISSION_REJECTED`，渠道退款命令保持为零。
升级前需确认旧版退款请求 Outbox 已排空，因为旧 mutation 的回执缺少支持新命令重放的原状态字段。

2026-11-18 本机 MySQL 验证中，V4 成功迁移。订单 567 在物流停机期间保留发货意图，退款失败且渠道命令为 0，
物流恢复后使用原参数重试，最终为 `SHIPPED`，仅有 1 张运单和 1 条发货事件。订单 568 先退款成功，发货返回
409，运单为 0。两笔终态订单均无残留发货意图。

### 发货持久化执行

commerce Flyway V39 新增 `fulfillment_shipment_jobs`。初始发货的一条记录同时保存受理参数、稳定命令 ID、
当前步骤和下一次执行时间。商家入口先落库，再尝试就地执行。操作待执行时返回 HTTP 202，商家可通过
`GET /api/merchant/orders/{id}/shipment-operation` 查看状态和错误码。

后台按租约领取待执行记录。订单意图与最终发货更新分别派生稳定 Order V1 命令 ID。物流按固定商家运单引用查询，
仅在渠道明确返回 404 时创建。写入物流投影与推进到订单更新步骤使用同一个本地事务。租约所有者才能推进流程。
自动重试有次数上限，耗尽或确认运单信息冲突时进入 `REVIEW_REQUIRED`，保留最后步骤及发货意图。

真实 MySQL V39 验证中，订单 576 在物流停机期间只提交一次发货并收到 HTTP 202，待办停在 `LOGISTICS`。
重启 commerce 并恢复物流后，后台将原操作推进到 `COMPLETED`。订单为 `SHIPPED`，仅有 1 张运单和
1 条发货事件，发货意图已清除。

升级前应排空 V39 之前的在途发货。旧版订单意图仅保存指纹，缺少可自动回放的原始参数，仍需用原请求恢复。

### 授权人工恢复

commerce Flyway V40 新增履约恢复审计记录。管理员在 `/api/admin/fulfillment/shipments` 查看待核对列表，
通过 `/{id}` 查看原操作和最近 100 条恢复记录，通过 `POST /{id}/retry` 提交 `recoveryId`、原
`commandId`、原因和核对证据。操作人 ID 来自登录会话。重放相同的恢复请求返回原审计记录，异内容返回冲突。

重新入队与保存审计同事务提交，仅允许无有效执行者的 `REVIEW_REQUIRED` 操作。原流程步骤、运单参数、命令
标识与订单发货意图保留，后台按原步骤继续执行。管理员从详情读取最新状态和原步骤错误，恢复记录保留重试前的错误。

真实 MySQL V40 验证中，测试订单 584 在物流停机期间进入 `REVIEW_REQUIRED/LOGISTICS`。商家恢复返回 403，
管理员恢复返回 202。物流启动后原操作完成，异证据重放返回 409，同请求重放保留原记录。最终只有 1 条恢复审计、
1 张运单、1 条发货事件，订单发货意图已清除。

### 修改运单版本保护

商家列表返回 `shipmentVersion`。修改运单请求必须携带页面读到的 `expectedVersion`，旧版本返回 409。
物流渠道在同一事务内检查并递增版本，商城物流投影只应用更高版本，Order V1 按商家归属、订单状态和前置版本
条件更新，并与 `SHIPMENT_UPDATED` 事件同事务提交。保留物流进度与运单详情各自的状态语义。

渠道已更新而订单尚未确认时，使用原参数和前置版本可以继续应用该次渠道结果。渠道只接受当前版本，或刚完成的
同参数重放。三处数据库迁移分别为订单 V5、商城 V41 和物流模拟器 V6，历史运单的初始版本为 0。

真实 MySQL 样本 595 先后完成版本 0→1→2。商家入口与物流渠道签名入口均拒绝旧请求并返回 409。
订单与商城、物流渠道三处均为版本 2、运单号 `CFL-595-C`，订单仅有 2 条修改运单事件。

### 接单与修改运单持久化执行

商城 Flyway V42 新增 `fulfillment_merchant_jobs`。接单和改运单先落任务，再调用下游。任务按订单、操作类型和
运单前置版本去重，进行中的同参数请求沿用原命令，异参数返回 409。接单直接执行 `ORDER` 步骤。改运单先在
`CHANNEL` 步骤更新渠道和商城物流投影，再保存检查点，使用相同命令 ID 提交 Order V1 修改。

同步完成返回 200。后台继续执行时返回 202，并通过 `Location` 提供
`/api/merchant/orders/{id}/fulfillment-operations/{commandId}`，提交操作的商家可查询步骤、状态与错误码。
后台通过租约和退避恢复待执行任务。同一 Order V1 命令的重放读取已保存结果。改运单的订单写被拒绝或任务耗尽
重试时进入 `REVIEW_REQUIRED`，供人工核对。

物流 HTTP 使用 2 秒连接超时和 3 秒读取超时。物流停机时，单次请求的等待时间受超时配置限制，后台按任务退避继续。

真实 MySQL 样本 601 在物流停机时收到 202。再次提交相同参数返回同一查询地址，同版本异参数返回 409。
商城停止期间，使用原参数由物流签名入口先提交版本 1。商城重启后，原任务自动从 `CHANNEL` 推进到 `COMPLETED`。
物流渠道、商城物流投影和订单均为版本 1、运单号 `RECOVERY-601`，接单和运单修改事件各 1 条。
V42 已通过 MySQL 空库安装与 V16 旧库升级验证。

### 接单和改运单的管理员恢复

商城 V43 新增 `fulfillment_merchant_recoveries`，通过内部外键绑定原命令。管理员在
`/api/admin/fulfillment/merchant-operations` 查看待核对任务，通过 `/{commandId}` 查询任务与最近 100 条审计，
通过 `POST /{commandId}/retry` 提交 `recoveryId`、原因和证据。操作人来自登录会话。

重新入队与写入审计在同一事务完成。仅接受无租约的 `REVIEW_REQUIRED` 操作，并沿用原步骤、命令 ID、运单前置版本
和请求内容。相同恢复请求返回原记录，变更操作人、原因或证据时返回 409。发货恢复继续使用原有入口。

真实 MySQL 样本 609 使用已保存的两条 Order V1 成功回执，模拟商城在收到结果前停机。两个执行者同时认领接单
只成功一次，租约过期后原命令自动完成。改运单从 `REVIEW_REQUIRED/ORDER` 经管理员重新入队后完成，商家恢复
请求返回 403，同请求重放返回原审计，异证据返回 409。最终两个 Inbox 结果保持一致，接单和改运单事件各
1 条，恢复审计 1 条，订单、商城物流投影和渠道运单均为版本 1。自动化集成测试也验证了失去租约的执行者无法推进
或完成任务。

## 6. V43 后的 CREATE 复核

**结论为 `REJECTED`。** 当前四张履约表已独立归属，待办租约按单个命令维护。Windows 与 WSL 审计分别在 commerce
和 order-db 执行只读快照，记录未决任务、超时租约、多未决任务订单、恢复孤儿、双向跨边界外键及发货意图。
不同数据库的审计各自取快照，最终迁移核对应在排空窗口重跑。

| 门禁 | V43 复核结论 |
| --- | --- |
| 接单、发货、改运单的订单写入 | Order V1 分别校验订单状态、商家归属和适用的库存或运单版本。发货意图与退款互斥。 |
| 单命令重放和并发执行 | 持久租约、Order V1 Inbox 及 V43 审计已覆盖同命令恢复。 |
| 同订单跨操作准入 | 接单和改运单按操作与版本去重，初始发货走另一张表。订单已推进、履约尚待核对时，下一种操作或下一运单版本仍可进入。 |
| Fulfillment V1 | 草案已校正为按状态准入，仅修改运单要求前置运单版本。调用方命令 ID、统一查询与可执行契约测试待实现。 |
| 边界依赖 | 履约 Mapper 消费者均位于履约内。运行时仍通过商城内 `LogisticsService` 和 `LogisticsGatewayClient` 写投影、访问渠道。独立服务适配时须保留物流所有权。 |

真实 MySQL 样本 611 在各下游操作已提交后，将对应的商城任务暂置为待核对，分别验证接单后发货、发货后改运单和
前一次改运单后再改三个场景。发货返回 202，审计同时检出 1 条待执行、1 条待核对和 1 个重叠订单。两次改运单
均返回 200，版本先后升至 1 和 2。演练恢复后，Windows 与 WSL 同样读到 33 条履约任务、0 条待执行、0 条待核对、
0 条到期租约、0 个未决任务重叠订单、0 条未清发货意图和 0 条跨履约边界外键。

## 7. V44 同订单准入与 Fulfillment V1

V44 增加 `fulfillment_order_locks` 和 `fulfillment_command_ids`。准入事务先取得订单锁，再识别同操作既有任务、
检查两张任务表的未决状态，并登记命令 ID、保存新任务。网络调用在事务提交后执行。待执行和待核对均阻止同订单
后续任务，人工恢复沿用原任务。既有命令 ID 在升级时回填，保留历史状态和恢复记录。

升级前排空旧版本执行者。已有重叠任务须通过 V43 审计查出并逐笔核对。V44 保留已有任务，重叠任务未清理前阻止
该订单的新受理。升级后 Windows 与 WSL 审计核对六张表、命令登记一致性和未决任务。

商城已提供 V1 提交和统一结果查询，既有商家 API 进入同一准入。MySQL 样本 612 上，前置任务被置为待核对后，
接单到发货、发货到改运单、上一版本到下一版本三次提交均被阻止。管理员恢复原命令后继续执行，最终运单版本 2，
接单和发货事件各 1 条，改运单事件 2 条。V1 同 ID 重放沿用原结果，异正文、旧版本与越权场景按契约返回。

## 8. V44 拆分前评审

### 物流写入和结果所有权

履约拥有商家命令、执行步骤与恢复决定。商城内 logistics 继续拥有物流投影、渠道签名与凭据、渠道调用、回调和
投影对账。订单状态与事件继续由 Order V1 提交。当前发货将商城物流投影绑定与履约步骤推进放在一笔本地事务，
改运单依靠渠道前置版本和商城投影重放。独立运行后，两边需要各自落下可查询的成功证据。

物流端口需覆盖建单、修改详情和按命令 ID 查询结果。商家运单引用继续使用现有稳定值，步骤命令 ID 从履约命令
与步骤派生。物流接收方先登记命令及归一化参数，再调用外部渠道，持久化投影与结果后才确认成功。同 ID 异正文
返回冲突，同 ID 同正文返回原结果。独立履约在本地按原租约推进，响应超时后通过原命令查结果或重放。

建单按原运单引用核对，查到的订单、承运商和初始运单号须与受理事实对应。改运单按前置版本核对，渠道版本进一步
推进后仍需能查到旧命令的原结果。若渠道接口只能查询当前资源，商城物流须保存已经确认的回执。渠道已接受但
回执尚无可靠证据时保留待核对。验收覆盖异正文、重复投递、回执丢失、渠道已完成但投影尚未完成，以及投影成功
后履约步骤尚未推进。签名密钥和回调接收地址继续归物流边界。

真实样本 614 验证了现有渠道行为。同一个运单引用以不同运单号重复建单返回 200 和原运单号。修改到版本 2 后重放

### 已知拒绝与重新受理

| 旧命令结果 | 同 ID 重放 | 新 ID 是否可受理 |
| --- | --- | --- |
| `CONFIRM/ORDER` 的 Order V1 回执为 `changed=0` | 返回原拒绝 | 订单重新为 `PAID` 且商家归属有效时，重新校验并取得同订单准入 |
| `SHIP/RESERVE` 的 Order V1 回执为 `changed=0` | 返回原拒绝 | 订单重新为 `CONFIRMED`、库存已提交且核对无未清发货意图或渠道效果后，重新取得准入 |
| 已发起物流写入、订单完成拒绝或结果未知 | 查询、核对或恢复原命令 | 继续占用准入，核对完成前拒绝新 ID |
| 成功完成 | 返回原成功结果 | 后续合法步骤或下一运单版本按各自条件受理 |

当前初始发货以订单为主键，商家任务以订单、操作和前置版本限制历史记录数，已知拒绝后新 ID 仍会碰到旧任务。
实现时按命令保留历史，并在 V44 订单锁内选择当前可执行尝试。只有订单原子回执与执行位置能证明可安全重试时，
才允许占用原业务位置的新命令。恢复审计仍绑定原命令及恢复 ID，查询旧命令继续返回旧结果。验收应覆盖两个新
ID 竞争、旧拒绝回执查询、已成功任务重复提交及可能产生物流效果时拒绝重开。

## 10. 独立履约影子运行

`fulfillment-shadow` 是显式 Compose Profile，包含独立 `fulfillment-service`、MySQL `fulfillment-db` 和一次性
只读授权服务。默认商城入口、履约写路径和物流所有权延续 V45。影子应用只包含复制、隔离、核对和命令结果查询，
签名业务写入口固定返回 503。目标库没有订单、资金或物流投影表。

```sh
docker compose -p fairy-commerceflow-shadow-qa -f compose.yaml -f infrastructure/compose/compose.fulfillment-shadow.yaml --profile fulfillment-shadow up -d --build --wait fulfillment-service
```

商城 V46 为六张履约表增加变更捕获。单行时钟与源写事务同提交，回滚不推进水位。快照和追平在商城 MySQL 的
同一可重复读快照中读取业务行、时钟和变更键。追平校验序列连续性，按当前快照合并同一主键的变化，再将目标
写入、隔离和水位一起提交。快照代次、水位重启后保留。当前实现会读全量六表和订单归属来计算隔离与摘要，
增量只应用变化行，适用于当前实验室规模。

目标只复制 V45 清单内六张表。缺少订单、商家归属、命令登记或父任务的记录进入隔离，关联记录同时排除在干净
数据外。订单与商城分别使用只读快照，订单不可用时，本轮保持原水位。后续轮次重新验证隔离证据，源记录删除或
归属恢复后清除隔离。报告按主键比较每张干净表的完整内容并计算 SHA-256。

影子 HTTP 发布在本机 `127.0.0.1:18091`。内部签名绑定 HTTP 方法、请求路径、Unix 秒时间戳、请求 UUID 和
正文 SHA-256，以上字段用换行连接后计算 HMAC-SHA256。签名和正文摘要使用十六进制。使用
`scripts/fulfillment/verify-fulfillment-shadow-runtime.ps1`
检查签名、关闭写入和同水位快照。包含源写入的验收环境应等待相同水位后再比较摘要。

真实 MySQL 演练中，同水位两次快照六表摘要一致，第二次写入 0 行。回滚保持源水位 0。一笔已提交的事务将
水位推进到 2，新增的有效锁被复制，缺少订单的锁被隔离。删除这两条演练数据后水位推进到 4，重启服务仍保持
该水位和快照代次。签名查询返回 200，错误商家返回 404，缺签名及正文篡改返回 401，合法签名的写请求返回 503。

完整快速回归后，Windows 和 WSL 在源目标水位 52 再次验证六表摘要一致，最终快照代次为 11。目标保留 25 条
发货任务、42 条商家任务、67 条命令登记、8 条订单锁及 5 条恢复审计，隔离为 0。V46 MySQL 迁移生命周期、
新服务 2 项及商城 53 项测试通过。

## 11. V47 切流前演练

V47 在商城库增加 `fulfillment_write_admission`，默认开放。准入事务读取单行开关并持有共享锁直到事务结束，

运维演练中用以下语句设置开关。冻结提交后检查未决任务、物流回执和源目标水位。恢复时等待提交，再检查同一

SELECT frozen FROM fulfillment_write_admission WHERE singleton_id = 1;

## 12. 默认关闭的独立执行

## 13. 真实物流桥与管理员恢复演练

## 14. 远程入口与原影子库转换

2. 停止原商城执行进程和目标影子进程，撤销旧商城账号对六张履约表的写权限，并确认有效写权限为零。

   后启动的旧影子实例无法写入。
4. 确认独立执行可用后，以远程路由启动商城。验收原命令、兼容发货、历史状态和管理员恢复，复核源水位未变化。

   本地执行。已有远程新写时以目标库为反向迁移源。重新建设影子前应先以恢复后的源库重做全量核对。

回退先停止远程执行，反向传回并逐行核对六表，恢复旧库权限及商城路由。原商家入口继续读取历史发货，运单推进

## 15. 权限交接与重启

V48 在商城冻结记录增加 `write_owner`，空库和升级默认均为 `COMMERCE`。所有者为 `FULFILLMENT` 时数据库
禁止解除冻结。商城启动时核对路由与持久化所有者，授权任务在发放权限前做同样的核对。执行配置下，旧商城账号
无权访问六张履约表，仍可读取所有者记录并正常访问其余商城边界。权限部署与所有者切换共享 MySQL 命名锁，
角色继承或存在同名其他 Host 的账号时执行配置拒绝发放授权。

默认使用 `compose.yaml`。受控窗口使用 [独立执行覆盖配置](../../infrastructure/compose/compose.fulfillment-execution.yaml) 为两个履约
入口、Order V1 身份和商城物流桥接线。配置要求分别提供业务、管理员、订单、物流的签名密钥。
目标服务仅在数据库已绑定 `EXECUTION` 后就绪。单纯加载覆盖配置无法变更源或目标的所有者。

1. 按上节冻结、排空、最终追平并保留两库核对与回退证据，停止商城和目标影子服务。
2. 在商城源库会话设置 `@expected_owner='COMMERCE'`、`@next_owner='FULFILLMENT'`、`@expected_source_sequence`，
   执行 [源所有者转换 SQL](../../infrastructure/commerce/transfer-fulfillment-source-owner.sql)。确认返回 `transferred=1`，
   运行执行覆盖配置下的 `commerce-source-access-freezer`，确认旧账号六表授权为 0。
3. 按上一节转换目标模式并验收，再使用同一覆盖配置启动履约服务和商城。重启仍使用该配置。期间使用实际运行账号
   确认六表写入被数据库拒绝。
4. 回退停止商城与独立执行。目标已有新写时先回传六表，核对行与历史审计，随后读取回传后的源水位。在目标库
   设置原交接的 generation 和源水位，运行 [目标退役 SQL](../../infrastructure/commerce/retire-fulfillment-execution.sql)，
   确认 `retired=1`。进入 `RETIRED` 的目标保留数据，旧执行配置无法启动。保持源冻结，用转换 SQL 从
   `FULFILLMENT` 改回 `COMMERCE`，再用默认配置运行授权任务恢复六表权限。核对权限后解除冻结，
   以默认配置启动商城。重新启用影子复制前必须完成全量核对。

隔离 Compose 使用两套独立 MySQL 实例和持久卷。错误源水位、未转换目标库和不匹配的部署均被拒绝。两库及
两应用重启并重新执行授权任务后，旧账号六表权限仍为 0，真实账号针对六表的 18 次增删改均返回 MySQL 1142；
其余商城权限可用。回退时正确水位才允许目标退役，恢复商城权限后，旧执行配置仍无法启动。

## 19. 正常发货的出库单和库存记账

| 服务 | 对出库流程负责的事实 |
| --- | --- |
| 订单 | 订单行 ID、商品、商家和数量。由 Order V1 给出履约所需的订单行。 |
| 履约 | 承接商家确认发货，复用持久化发货任务 ID 作为出库单号，推进出库记账、物流建单和订单发货。 |
| 库存 | 校验出库数量与已提交的库存分配相符，记录出库单和单行库存流水，在同一个 MySQL 事务中写入事件 Outbox。 |
| 物流 | 保存运单和承运进度，异步更新运输、签收状态。 |

执行模式下，履约在订单发货准入成功后，使用签名的 Inventory V1 接口提交出库单，收到确认后创建物流单并推进订单发货。
当前订单模型每单一次发货，要求同一商家拥有所有订单行。多商家或拆包发货需要独立包裹和分批数量模型。
中断恢复使用原发货任务 ID，再次提交相同出库单会返回原结果。已经到达物流或订单完成步骤的在途任务也会确认库存出库单。

库存付款提交时已将数量从预占转为已售。发货写入 `OUTBOUND_POSTED` 的物理出库数量和余额快照，避免对可售、预占或
已售余额重复扣记。`outboundId + orderLineId` 唯一识别出库行，同一原订单行只能记一次。变更已提交的单据内容或换单号
重复出库会拒绝。库存库 V4 同一事务写入出库单、出库行、库存流水和事件行；任意一行失败时整单回滚。

库存服务把 Outbox 中的 `INVENTORY_OUTBOUND_POSTED` 异步发布到 `inventory-outbound-events`。
收到 Kafka 确认才标记发布完成。发布语义为至少一次，事件 ID 基于出库单号和订单行 ID，供下游幂等消费。
跨服务只传合同字段，订单、履约、库存和物流各自写入所属数据库。

隔离 MySQL 和 Kafka 验收中，订单 1 经商城下单、支付、接单和发货，订单行 1 的两件商品生成一条流水和一个 Kafka 事件，
可售余额没有二次扣减。原单重试返回同一回执，改单数量和换单号均被拒绝。双商品测试让第二行 Outbox 写入失败，
确认整单回滚，移除测试故障后使用原单号一次补齐。停机期间的 Kafka 待发布事件在恢复后发布，原记账流水保留。
本阶段保留的五笔缺证测试记录后来已[单独归档](INVENTORY-RECONCILIATION-REVIEW.md#本地测试数据最终处置)。

## 20. 出库监控、带存量升级与履约重启

库存服务从出库 Outbox 发布待发布数和最老积压时长，并记录发布或确认写回失败次数。Prometheus 单独抓取库存服务。
库存服务拥有记账和发布状态，履约服务拥有发货步骤。排查时用同一出库单号核对库存流水、Outbox 和履约任务步骤，
区分未记账、已记账但待发布、已记账但物流尚未推进三种状态。见[告警配置](../ALERTING.md)。

在独立 Compose 项目中从 V3 源码构建基线。先用真实接口生成已支付订单和库存分配，并用合成已送达订单登记仓库凭证。
升级时只替换隔离项目的库存镜像，沿用同一 MySQL 卷。对八张已有表逐表比较有序全量行的 SHA-256，
并确认 V4 新表初始为空。演练在库存出库成功、履约停在物流步骤时重启履约服务，恢复后继续使用原任务和原出库单。

- V3 基线来自 `d3399d6`。八张原表共 16 行，升级前后逐表行数和摘要一致，切流标记保留。
  V4 三张出库新表初始均为 0 行。
- 订单 1 的库存事务提交后，物流停机使履约任务保留在 `PENDING / LOGISTICS`，此时订单仍为 `CONFIRMED`。
  重启履约并恢复物流后，原任务推进至完成，产生一个运单，仍只有一条出库行、一条出库流水和一条事件。库存余额未重复扣减。
- Kafka 停机期间，隔离 Prometheus 采到待发布数 1、最老积压 14 秒、失败次数 3，发布失败告警进入 firing。
  Kafka 恢复后原事件获确认，待发布数和最老积压归零。积压告警阈值和清零由 Promtool 独立验证。

## 33. WMS 退货实收与质检验收

库存服务通过签名查询提供原出库凭证，按订单、订单行、商家、商品、可选仓号及原包裹交叉核对。
唯一凭证可自动带入，有多个可选包裹时由顾客选择。结算快照继续负责计算退款金额和运费。

商城 V63 保存 WMS 状态投影。WMS V2 使用售后单号作为稳定退货单号，在物流送达后受理，
独立记录实收和质检时间。同一回执可以重复读取，已确认的数量和结果发生冲突时拒绝改写。
仓库足量实收且质检合格才允许商家验收。商家确认后，支付结果成功才触发原仓库存回补。
短收、拒收和质检不合格进入待复核。存量在途退货从原出库凭证补齐关联，来源无法唯一确定时进入待复核。

隔离和日常均运行 [PowerShell 7 验收脚本](../../scripts/commerce/verify-merchant-operations.ps1) 的 `WmsReturn` 章节。
隔离模式传入独立项目以及商城、支付、物流和 WMS 后台地址。日常使用以下命令。

```powershell
pwsh -NoProfile -File scripts/commerce/verify-merchant-operations.ps1 -Chapter WmsReturn
```

## 34. 售后异常工单验收

同一售后单只生成一张工单。商家仅可处理本店工单，同一处置请求可以重试。
