## 6. 通知历史迁移验收

旧商城通知表冻结且库表已建成后，可手工运行一次性工具。默认启动链路不包含该工具，数据库凭据由一次性容器使用。

```powershell
docker compose --profile notification-migration run --rm --no-deps notification-data-migrator --check
docker compose --profile notification-migration run --rm --no-deps notification-data-migrator --complete
```

`--check` 在事务中演练回填并回滚行变更，MySQL 可能已分配自增号。有历史通知时先在隔离副本演练。
`--complete` 在同一事务中按 eventId 补齐历史通知，核对已发布事件对应的通知正文、业务字段和独立消费 Inbox，
确认没有缺失、冲突或无来源通知后，再写入历史水位和通过记录。已经读过的目标通知保留首次已读时间。
工具不会投递 Kafka 消息。若核对期间刚好有新通知到达目标而源快照尚未包含对应的已发布事件，等待投递追平后复查。

- 隔离 MySQL 8.4 使用现有库的 301 条已发布事件及对应通知和 Inbox，并添加 3 条旧通知样本，历史主键为 2、5、8。
  首次回填只插入缺失的 1 条，恢复 1 条历史已读记录，保留目标原有首次已读时间。水位为 8，目标 304 个不同 eventId。
  重跑后通知、Inbox、水位、完成时间及核对记录逐行一致。正文冲突、缺失 Inbox 和无来源通知分别验证会拒绝登记。
- 现有商城旧通知和旧 Inbox 均为 0。依 Outbox 主键逐条核对了原 298 个 eventId 和随后新增的 3 个，均匹配目标通知
  和独立 Inbox。目标隔离表为 0。按主键升序，以制表符连接主键和 eventId，行间用 LF、结尾不加换行计算 SHA-256。

  | 核对范围 | 行数 | SHA-256 |
  | --- | --- | --- |
  | 原 Outbox 主键 1–298 | 298 | `b06362c5dd7df6e7876b2798af18c8b42b36ae40520af7f84dd8cd2c607d44f7` |
  | 当前 Outbox 主键 1–301 | 301 | `e7cbd9dedc83a39ba1e186e32d5fe8226af6cacb54499236606b98785c604961` |

- 2026-11-19 在现有通知库登记 `backfill_completed=1`、`source_watermark=0`，核对记录为 301 项匹配，
  缺失、孤儿和冲突均为 0。再次运行保留原完成时间和唯一核对记录。通知和 Inbox 快照摘要在登记前后相同。
  登记后从门户查询演示顾客通知，返回的 20 个 eventId 各不相同。
- 只读复核库存历史订单 465、479、480、497、498 仍挂账，尝试次数各为 5，结案记录为 0。旧预占未重放。
