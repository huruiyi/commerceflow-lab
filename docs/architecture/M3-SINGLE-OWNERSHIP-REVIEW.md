# M3 单一所有权复核与迁移收尾

## 1. 复核结论

2026-11-18 对本地 CommerceFlow Lab 做只读复核。六个内部服务均已切换到各自的 MySQL；六个目标库及商城库
均无跨 Schema 外键。商城的业务请求经签名 API 或消息交给对应所有者。支付和物流模拟器属于外部平台边界。

**运行路径的切换已完成，M3 迁移收尾仍未关闭。** 库存旧迁移入口已封住，库存与支付有存量对账待处理，
目录和通知旧表仍有商城运行授权。现阶段继续使用 MySQL，
PostgreSQL 专项按[数据库演进计划](DATABASE-EVOLUTION-PLAN.md)另行评审。

## 3. 剩余工作及完成标准

### 优先阻止旧迁移入口覆盖库存目标

- [x] 旧迁移入口先检查目标切流标记及五表占用，确认可迁移后才访问源库。导入事务再次校验，已移除清表操作。
  隔离库验证了已切流、已有数据、导入前并发新增及指纹不匹配四类拒绝，空库导入五表逐行一致。
- [x] 现有库核对库存余额、预占和销售数量、库存记录引用及 Inbox 后登记 `CUTOVER_COMPLETE`。
  登记前后库存五表 3012 行的 SHA-256 摘要一致，商城命令投递 Outbox 摘要一致，35 条库存待对账保留。

### 对清库存与支付历史异常

- [ ] 按原命令与订单逐笔核对库存 35 条超时 `RESERVE`。这批命令关联 35 个仍存在的订单，商城结果 Inbox
  和目标库存 Inbox 均无原命令命中，库存库也无这些订单的预占行。28 个订单库存仍为待对账，7 个订单已取消释放；
  业务订单状态还包括已付款、已收货、已完成和已退款。逐笔确定终态与补救方式，再通过受控恢复流程留下审计。
  补查订单 485 等待预占及缺少投递记录的原因。验收产物包含逐笔结论和可复跑的未决清单。
- [ ] 处理支付库 4 条 `PAYMENT_TIMEOUT/OPEN`。关联支付均为 `CLOSED`，检测时间在正式支付切流前。对照渠道和订单
  事实决定结案方式并留审计。增加按真实对账表状态的只读统计或告警，验收时与 Process Manager 指标分别核对。
  当前 Process Manager 计数为 0，四条 OPEN 来自另一张账本。

### 收回历史权限并隔离一次性工具

- [ ] 从商城账户授权生成器明确排除目录旧三表、通知旧五表及三张已停用的订单/支付影子捕获表（
  `order_shadow_change_clock`、`payment_shadow_change_clock`、`payment_shadow_change_log`）。
  当前这 11 张表合计 44 项直接授权。更新后用真实运行账号验证增删改被拒绝，并重跑正常业务链路。
- [ ] 目录的默认启动路径去掉带 root 凭据的迁移依赖。先提供独立的全新库初始化与旧库迁移两种明确入口；以
  `COMPLETE` 已切流库的重启和新库启动验证无回灌依赖。通知保留 298 项 eventId 的核对证据，
  收尾目标标记并验证有历史数据环境的回填证据。随后把库存、目录及三套影子工具从常驻启动和运行账号隔离。
- [ ] 移出常驻支付容器的源库凭据，封存订单和支付影子开关与迁移访问。撤销已退出的履约影子账号对商城三个影子对象
  和订单库三个列的授权。复跑部署和恢复时核对旧水位、目标行数及授权。商城源库的 `commerceflow@%` 仍有
  Schema 级权限，应核对其迁移、运维和其他调用方后再缩减使用范围。
