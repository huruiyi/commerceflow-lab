## 1. 交付顺序与依赖

1. 沿用已验收的隔离快速与完整入口，继续对齐空卷和升级恢复专项的生命周期基线。
2. 对当前通知 Compose、控制台和告警候选版本完成隔离重建、现役与回退角色检查、旧库与空卷验证。日常发布按候选版本和维护窗口独立验收。工作区与日常现役的差异以发布记录核实。
3. 推进自动化门禁、定期恢复演练、运行仪表板和服务所有权验收。用真实负载和数据增长确定性能目标。
4. 根据负载、恢复目标或新的业务依赖，决定是否启动容量、HA、平台接入或服务拆分。真实渠道和共享部署进入单独验收。

## 6. 微服务演进准入

M3 已按通知、目录、库存、订单、支付编排、履约的顺序完成单一所有权交接。商城的其余业务继续按模块治理。支付、物流及其他模拟器代表外部平台。[M3 前置审计](M3-PRE-SPLIT-AUDIT.md) · [M3 正式验收](M3-SINGLE-OWNERSHIP-REVIEW.md#14-2026-11-21-日常发布与-m3-验收)

1. 先确认独立数据所有权、部署周期、故障隔离或容量收益，核对收益和事务及运维成本。现有模块须有自动依赖检查，跨边界使用应用接口和事件。
2. 冻结版本化 API 与事件、消费者契约、W3C Trace、超时与错误语义。验证并发、重放、迟到、部分失败和人工恢复，检查原业务 ID 的幂等约束。
3. 一次只交接一个边界。隔离验证备份、迁移、停写、排空、最终核对、撤权和回退，覆盖空库、旧库与新增业务数据。禁止跨服务共享 Mapper、Schema 或跨库 JOIN。过渡接口和权限按 [兼容退出门禁](../VERIFICATION-SYSTEM.md#12-临时兼容退出验收) 退役。
4. 使用本地事务、Outbox/Inbox、幂等标识和可观察补偿，维持唯一权威写入方。沿用当前签名协议、协议资源名、锁顺序及事务边界。全局事务继续按本地事务与补偿设计，Seata、DTM 不在现行方案内。数据库迁移按第 5 节独立评审。
