# Fulfillment V1 契约草案

本草案用于 CREATE 准入。当前商家 HTTP 接口沿用既有请求和响应，V1 尚无远程运行入口。

- 写操作为 `CONFIRM`、`SHIP`、`UPDATE_SHIPMENT`。请求包含 `version=1`、`commandId`、可信
  `merchantId`、`orderId`、该操作的参数、前置订单版本及发生时间。传输携带 Trace 上下文与内部签名。
- 发货和修改运单要求承运商及运单号，按现有长度约束归一化。接收方根据操作、商家、订单、前置版本和归一化
  参数计算业务指纹。传输签名、发生时间和 Trace 属于附带信息。
- 同 ID 同指纹返回已受理的同一操作及其当前结果。同 ID 异指纹返回冲突。不同命令对同一订单的并发执行受持久
  条件约束。命令结果查询按商家和命令标识授权，订单归属错误返回不存在。
- 受理只说明命令已落库。结果包含 `commandId`、当前步骤、处理状态、结果版本和稳定错误码。前置条件拒绝与
  未知结果需要分别表示。只有订单和物流步骤均有成功证据才报告发货成功。
- 下游每个步骤使用从原操作派生的独立稳定 ID。接收方需要按 ID 重放原结果，订单状态更新与对应事件同事务落库。
  超时继续查询或重放原步骤。人工恢复使用独立授权并记录人员、原因和证据。
- 商家列表由 commerce 聚合订单与退款展示。未来可增加只读履约进度字段，页面投影无需参与写操作准入。
